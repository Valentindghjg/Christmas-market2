## 2. Authority and service boundaries
- SessionService: player/company join, ownership, lifecycle and cleanup (implemented as `SaveSlotService`; its save-to-server map is `SaveLocatorService`, CM2-S3).
- CompanyService: save ownership and membership (Solo/Duo/Trio/Quad, owner + members, 5-digit invite code, one server per save; PRODUCT_SPEC.md, owner decisions 2026-11-21).
- PlotService: plot allocation, boundaries, plot ownership and access.
- EconomyService: all money movement and immutable transaction IDs.
- SupplierService: catalog, unlocks, order validation and quote creation.
- DeliveryService: order state machine, ETA, arrival and unloading.
- InventoryService: unique stock item IDs, capacity and atomic lifecycle.
- PlacementService: bounded transforms, collision checks, plot persistence.
- PricingService: manual/auto prices and effective price at reservation time.
- CustomerService: NPC spawning, preferences, FSM and pathfinding budgets. CM2-N1: the walking customers' director is `CustomerNpcService` (FSM, queue, budget 4 per plot and 24 per server, cleanup; headless-safe, its world adapter injected). Routes come from `NpcPath` (pure lot-frame router over the known keep-clear boxes; no PathfindingService). The Roblox side is `CustomerNpcWorld` (adapter) and `NpcAvatar` (default R15 template, own beanie and scarf Parts, collision groups `CustomerNpc`/`LotTree`/`PlayerCharacter`). Money and stock change only in `CompanyStateService`'s server-trusted `npc*` methods inside the company's critical section; no remote reaches them. Parking claims (`session.npcClaims`) and session tokens are runtime only; reservations are cleared on every load. CM2-N2: `checkout(companyId, plotId)`, prompt validated in `main.server` (`checkoutAt`).
- CheckoutService: reserve, queue, finalize sale, rollback/cancel.
- EmployeeService: hire once, task assignment, job lease and completion.
- Staff (CM2-25/26): the director is `StaffNpcService` (headless like `CustomerNpcService`; requires only GameConfig, NpcPath and `Staff`; injected `companies`, `plotOf`, `world`, `now`). Staff ID `<companyId>|<role>`, load staff `staffload:<seq>`; budget 3 per plot (one per role), 18 per server (`GameConfig.Staff`); tick 0.25 s; FSM `StaffNpcService.Fsm` (WalkingToPost, OnDuty, Idle, WalkingToPickup, CarryingToCar, WalkingToBay, CarryingToSpot, WalkingToBreak, Resting, LoadLoop; leg states time out after `LegTimeoutSeconds` with a snap). Stationary staff (OnDuty, Idle, Resting) have an anchored root. Orders and stock change only in `CompanyStaff` (a mixin installed into `CompanyStateService`: `getStaffView`, `setStaffEnergy`, `staffPeekOrder`, `staffClaimOrder`, `staffLoadOrder`, `staffReleaseOrder`, `staffPeekRestock`, `staffRestock`) inside the company's critical section; the Lot Worker carries orders as `Staff.CarrierUserId` 0 (players get `AlreadyCarried`; a reload clears it) and restocks the runtime sold-spot list `session.vacatedSpots` (filled by `npcSettle`, cap 20, not saved) with one `PlacementService.stockFromBay` (ID prefix `staff:<revision>:<clock>`). Energy is copied into `staffEnergy` every 15 s without a dirty flag. `CustomerNpcService` gets `deps.staff` and serves the counter only while `staff:cashierReady(companyId)`. The Roblox side is `StaffNpcWorld` (uniformed `NpcAvatar.build(NpcLook.forStaff(role))` in the plot's `Staff` folder, and `syncBreakArea` for the Part-built campfire `BreakArea` with plot attributes `BreakAreaX/Z/Rotation`). No wages: no staff code path debits cash.
- ProgressionService: prerequisites, HQ/parking/land unlocks.
- QuestService: event counters, rewards and idempotent claims.
- AnalyticsService: aggregate counters and bounded history.
- MonetizationService (CM2-46a, `docs/plans/CM2-46a.md`, as built): headless with injected deps (`main.server.lua` wires `MarketplaceService` and `Players`). All 27 reference products live in `src/shared/ShopConfig.lua` with every `id = 0` (the owner creates the passes and developer products and enters their IDs; engineering creates and publishes nothing). `ProcessReceipt` grants a developer product only into the buyer's active, available save: it waits for one (every `ReceiptPollSeconds` 2 s, at most `ReceiptWaitSeconds` 60 s, only while the buyer is in the server), binds the purchase to that save in the player ledger (`PurchaseLedgerService`) before the grant, grants and saves the company record with the receipt ID in it (`CompanyPurchases.grantPurchase`), records the purchase as done in the ledger and only then returns `PurchaseGranted`; the purchase effect (Hot Cider Round's staff rest, the thanks notice) follows the live record: it runs once when the grant is written into the live record, also when the save after it fails, and a retry that finds the receipt runs no second effect (Amendment 1); any failure, an unknown product ID, a second call for an ID in flight or a purchase bound to another save that a live session holds returns `NotProcessedYet`. A purchase bound to another save X is finished without a grant when X's record holds the receipt (`PersistenceService:peekReceipt` = `Applied`) and moved to the current save when X has no unexpired lock (`Free`). Game passes are checked on join (`UserOwnsGamePassAsync`) and after `PromptGamePassPurchaseFinished`; a pass perk applies to a save while at least one of its players on this server owns the pass (runtime `CompanyStateService:setPerks`, never saved). Effects: Golden Till ×2 and Cash Rush ×2 on customer sale cash (×4 with both; the bonus counts as revenue), Shining Star ×2 review reputation, Express Sleigh delivers at once, Evergreen VIP +1 review star (max 5) and customers pay up to 15 % over budget, Hot Cider Round rests every role. Robux spent = receipt `CurrencySpent` (Robux only) plus each owned pass's price once (live price, else the config price). Only the server prompts, never for an ID of 0 or a product with `ready = false`. No product grants a random reward; paid random items only from version 2 with PolicyService checks (PRODUCT_SPEC.md, owner decisions 2026-11-21).
- PersistenceService: schema migrations, lock acquisition, save/retry/release.

Use dependency injection or explicit initialization ordering; avoid circular requires. Shared modules are data and pure logic only, never grant currency.

## 3. Network contract
All client-to-server calls are untrusted. Use a small versioned action protocol, not arbitrary client-defined price/cash/item payloads. Example action names:
`Supplier.RequestQuote`, `Supplier.PlaceOrder`, `Stock.Place`, `Stock.Store` (CM2-G14; they replace `Delivery.Unload`, `Inventory.Place` and `Inventory.Pickup`, which now return `UnknownAction`), `Pricing.SetMediumPrice`, `Pricing.SetAuto`, `Employee.Hire` (CM2-25/26 part b: payload exactly `{employeeId}` with `Cashier`, `LotWorker` or `LotManager`, else `UnknownEmployee`; the server checks in this order `UnknownEmployee`, `AlreadyHired`, `EmployeeLocked` (the save's HQ level is below the employee's `requiredHqTier`: the Lot Manager needs HQ 4, CM2-G9a), `EmployeeCapacity` (hired Cashier + Lot Worker + Lot Manager reaches the HQ tier's `employeeCapacity`: 2, 3, 5, 6), `InsufficientFunds`, then debits `hireCost` once, adds it to `spent`, records `EmployeeHired` and sets the employee's energy to 100; a replayed request ID is `DuplicateRequest`), `Staff.MoveBreakArea` (CM2-25/26 part b, any save member: payload exactly `{x, z, rotation}`, x and z finite on the 0.5 grid with |v| ≤ `Placement.CoordinateLimit`, rotation 0/90/180/270, else `InvalidBreakArea`; the server checks the spot with `Staff.checkBreakArea` against the lot, keep-clear boxes, decor fences and trees (`OutsideLot`, `KeepClear`, `TooClose`), saves `breakArea`, returns the new area and moves the break-area model; resting staff walk to the new spot; default per-action limit 10 per 10 s plus the global limit), `Progression.BuyLotExpansion` / `Progression.BuyParking` / `Progression.BuyHQ` (CM2-G9a: payloads exactly `{level}` integer 1..6, `{tier}` integer 2..2 and `{level}` integer 2..4, else `UnexpectedField` for other keys and `InvalidLevel` / `InvalidTier` / `InvalidHQ` for the value; the server checks with `Progression.check` in this order `InvalidLevel`, `AlreadyOwned` (target ≤ current), `NotNextLevel` (target > current + 1), then the first unmet requirement row: `PrerequisitesNotMet` (HQ level, lot level, parking tier), `InsufficientReputation`, `InsufficientFunds`; then debits `cashCost` once (events `LotExpansion`, `Parking`, `HQUpgrade`), sets the level and returns it; a replayed request ID is `DuplicateRequest`, a second request for the same level `AlreadyOwned`; any member; `Company.GetSummary` carries `progression` with each kind's next offer, its requirement rows `{id, have, need, met}`, unlocks and the workshop), `Company.Invite`, `Company.SetRole`, `Quest.Claim`, `Order.Carry`, `Order.Load`, `Order.Release`, `Supplier.SellBack` (implemented 2026-11-21; order interactions also arrive through server-side ProximityPrompts that are validated like remote calls, including a server reach check), `Lot.Like` (CM2-G15: payload exactly `{plotId}` with a plot ID from `GameConfig.PersonalPlotIds`, else `UnexpectedField`/`InvalidPlotId`; handled in `main.server.lua`, never by `companies:handle`, which answers `Forbidden`; rate limits 5 per 60 s per player plus the shared global and per-action limits (`RateLimited`); the liked save comes from the plot claim (`LotUnavailable` for a free plot), the liker must be within reach of that lot's sign (`OutOfReach`), may not be the owner or a member of the liked save (`OwnLot`), and likes a lot once per UTC day (`AlreadyLikedToday`, at most 100 likers per lot and day, `LikesFull`); success returns the liked record's revision and `data.likes`).
Shop actions (CM2-46a) travel through their own RemoteFunction `Remotes.ShopAction` and `MonetizationService:handle`, with the same envelope (`Protocol.validateShopRequest`, `Protocol.ShopActions`): `Shop.Catalog` (payload `{}`, else `UnexpectedField`) returns `data = {products = {{key, category, kind, price, state, grant}}, robuxSpent}` in config order, state `ComingSoon` (id 0 or not ready), `Owned` (owned pass, or a per-player product in the ledger's unlocks) or `Buy`; `Shop.Prompt` (payload exactly `{productKey}`, else `UnexpectedField`; a key failing `ShopConfig.isKey` is `InvalidProduct`) checks in this order `UnknownProduct`, `ComingSoon`, `AlreadyOwned`, `ShopUnavailable` (a per-player product without a cached ledger), `NoActiveSave` (a developer product without an available active save), `BoostFull` (Cash Rush would pass `BoostCapSeconds`), `PromptFailed` (the prompt call errored) and answers `{ok = true}` after the server prompted; rate limit `ShopLimit` 10 per 10 s per player (`RateLimited`). A successful prompt grants nothing: only the receipt does.

Request: `{version=1, requestId=<UUID>, action=<enum>, payload=<validated fields>}`. Response: `{ok, errorCode?, revision?, data?}`. Request IDs deduplicate financial actions within a session and persisted recent IDs where needed. Validate types, lengths, ranges, enum values, plot ownership, proximity where applicable, server-derived prices and role permissions. Per-action rate limits; never trust a client-supplied purchase cost, sale result, or inventory quantity.

Server->client: a one-way `Notify` RemoteEvent carries localized notice keys (customer reviews, wrong car, out of reach). Filtered state snapshots on join and revisioned deltas after mutations. Client can optimistically animate UI but server state wins. Avoid broadcasting private company details to other plots.

## 4. Data model (schema v1 proposal)
```lua
{
 schemaVersion = 1,
 companyId = "personal:<userId>" or "shared:<uuid>",
 ownerUserId = 123,
 mode = "personal" or "shared",
 members = { ["123"] = "Owner" },
 cash = 0, reputation = 0,
 inventory = {
   items = { [itemId] = { speciesId, sizeId, state, plotId, transform, orderId } },
   pendingOrders = { [orderId] = { requestId, lines, createdAt, dueAt, state } }
 },
 pricing = { medium = { [speciesId] = 82 }, automatic = false },
 progression = { hqTier = 1, landLevel = 0, parkingSpaces = 0, unlocks = {} },
 staff = { cashier = 0, lotWorker = 0 },
 layout = { placements = {} },
 quests = { counters = {}, claims = {} },
 stats = { lifetimeSales = 0, revenue = 0, visits = 0, lost = 0, bySpecies = {} },
 history = {}, recentRequests = {}, updatedAt = 0
}
```
Schema is a proposal; existing `BusinessState.lua` currently uses a simpler v1 shape and must be migrated carefully before production. Keep all persisted numeric values finite, capped and serializable. Store transforms as numeric arrays, not Instances/CFrames.

**Save slots (CM2-S1, implemented 2026-11-22).** Each player owns a profile that lists their saves; each save is its own company record.
- **Company schema 11** (`BusinessState.SCHEMA_VERSION = 11`): adds `saveName` (valid UTF-8, 1–24 code points) and `saveSize` (`Solo`, `Duo`, `Trio`, `Quad`; S1 writes `Solo`). Migration 10 → 11 sets the default name `Tree Lot 1` when the name is missing or invalid and `saveSize = "Solo"`; the v1 path sets both. The save's company ID is `save:<saveId>`. `validate` ignores the persistence envelope fields `_session`, `_deletedAt`, `_migratedTo`, `_migratedAt` and `_migratedFrom`. In S1 the profile entry's name is the source; the record's `saveName` is a copy written on every load and on renaming the active save.
- **Save ID (fix round 2):** `<ownerUserId>_<16 lowercase hex>`, at most 36 chars (`SaveProfile.SAVE_ID_MAX_LENGTH`). `SaveProfile.newSaveId(userId, guid)` takes the GUID from `HttpService:GenerateGUID(false)`, drops the hyphens, lowercases it and keeps characters 17–32; the user ID is written by `SaveProfile.userIdText` (`string.format("%d", userId)`, because `tostring` writes 19-digit numbers in exponent form). `SaveProfile.isSaveId`: a string of at most 36 bytes matching `^(%d+)_(%x+)$` with 1–19 digits, exactly 16 hex characters and no uppercase. The user-ID prefix makes IDs unique across players; within one player 62 random bits remain, and a collision fails closed (`ProfileCorrupt` on Create, `SaveDeleted` on Play) without data loss. IDs are never reused; deleted saves keep a tombstone.
- **Profile schema v1** (`SaveProfile.lua`, `SaveProfile.VERSION = 1`):
```lua
{ profileVersion = 1, userId = 123, createdAt = 0, updatedAt = 0,
  saves = { { saveId, name, role = "Owner", size = "Solo", createdAt, lastPlayedAt } }, -- creation order
  nextSaveNumber = 1, lastSaveId = nil, legacyState = "Pending" | "Done" | "None",
  legacySaveId = nil, recentCreates = { { requestId, saveId } } }                      -- newest last, at most 10
```
`validate` also accepts role `Member` and sizes Duo/Trio/Quad, and rejects duplicate save IDs and more than `GameConfig.Saves.MaxSavesPerPlayer` (50) entries. Names are trimmed, single-spaced, 1–24 code points, no control characters and no `#`; they are filtered with `TextService` at submission (the broadcast result must equal the name).

## 5. Persistence and concurrency
DataStore keys scoped by company ID; use UpdateAsync-based session lock with job ID and expiry/heartbeat, not a naive GetAsync/SetAsync last-write-wins. Acquire lock before enabling writes; renew while active; release at leave/shutdown; recover expired locks with a safety margin. Save after significant actions (debounced) plus periodic autosave and BindToClose; retries with exponential backoff and budget awareness. If load fails, block financial actions instead of creating a fresh default and overwriting existing progress. Use versioned migration functions and backup/rollback strategy. Shared-company single-writer policy; conflicts must not fork balances.

**Implemented policy (2026-11-21):** a company record is one DataStore key holding cash, inventory, orders, placements and recent request IDs together. Mutations run to completion inside the company critical section without yielding and only mark the session dirty; `CompanyStateService:flushDirty()` writes dirty sessions every `GameConfig.SaveFlushSeconds` (15 s) and re-saves every session at least every `AutosaveSeconds` (60 s) to renew the `SessionLockSeconds` (120 s) lock. Leave, switch and shutdown perform a final save (CM2-R5): a failed final save is retried after 2, 4, 8, 16, 16, 16 and 16 s (`GameConfig.UnloadRetry`), for at most `SaveFailClosedSeconds` and at most 18 s after shutdown begins; the lock and the save-to-server map entry are released only after a successful save, otherwise they expire; a switch away from a healthy save that cannot be stored keeps the player on it (`SwitchSaveFailed`); a Play of that save during the retry gets `SessionBusy`. A crash can therefore lose at most one flush interval, but never persists a debit without its effect. Transient save failures are retried on the next flush; lock loss, an invalid record, or `SaveFailClosedSeconds` (90 s) without a successful save stops mutations. A runtime error inside a critical section fails that session closed and it is never saved again. Robux receipts (CM2-46a) save the company record right after the grant and return `PurchaseGranted` only after that save and the ledger finish succeed; otherwise `NotProcessedYet`, and the retry finds the receipt in the record. The purchase effect (staff rest, notice) follows the live record and runs once per grant (section 2).

**Save slots (CM2-S1, implemented 2026-11-22).** `SaveSlotService` fills the SessionService role of section 2: profile I/O, the legacy migration call, the `Save.*` actions (`Remotes.SaveAction`), play, switch, leave, the teleport seam and the active-save registry. Since CM2-RF the code is split into `SaveSlotService` (core) and the parts `SaveSlotPicker`, `SaveSlotTeam`, `SaveSlotCrossServer` and `SaveSlotShared`; the parts add methods to the one class.

|---|---|---|
| `ChristmasMarket2_CompanyState_v1` (`PersistenceService.STORE_NAME`) | `company:personal:<userId>` | The legacy record. Never deleted or overwritten again; only `_migratedTo`, `_migratedAt` and `_session` change |
| same store | `company:save:<saveId>` | One company record per save, with its own session lock |

Every key contains the user ID as a fixed substring, so RTBF erasure templates can match it. Store names are not scoped by environment (out of scope). `Profiles_v1` held only Studio test profiles with old 32-hex save IDs that the current `isSaveId` rejects; it is abandoned and never read.

Rule for S2 and S3: a key holding a save ID gets a prefix of at most 14 chars; a key holding a user ID, at most 31. Every new key family adds a row here and a case to the key-length test (SaveSlotService_Test "keeps every key within 50 characters for a 19-digit user ID"). S2 member lists stay inside the company record (no new key). Every fake DataStore in the tests enforces the 50-character limit.
- **Lock-free profile:** every profile change is one `UpdateAsync` transform applied to the stored value (3 attempts, 1 s and 2 s apart), so a second server can never lose an update and S2 can write to another player's profile. Transforms reset their results at the start (they can run more than once). An unreadable profile fails with `ProfileUnavailable`, an invalid one with `ProfileCorrupt`; neither is ever overwritten with a fresh default.
- **Legacy migration** (`PersistenceService:migrateLegacy(userId, saveId, saveName)`, called on the first profile open while `legacyState = "Pending"`): a. `UpdateAsync(company:personal:<userId>)`: absent → `NoLegacy` (no write); already `_migratedTo` → that save ID wins; locked by another unexpired server → `SessionLocked`; otherwise take a deep copy without `_session` and write our lock. b. migrate the copy to the current schema as `save:<saveId>` with `saveName`, `saveSize = "Solo"` and `_migratedFrom = <legacy key>`; on failure return `MigrationFailed`. c. `UpdateAsync(company:save:<saveId>)`: absent → write the record without `_session`; `_migratedFrom` equal → no write (idempotent); anything else → `MigrationConflict`. d. `UpdateAsync(legacy)`: when the lock is ours or absent, set `_migratedTo` and `_migratedAt` and clear `_session`; the data stays unchanged; another job's lock → `SessionLocked`, a non-table record → `MigrationFailed` (no write). Store errors after retries return `LoadFailed`. Steps b–d run in `_finishMigration` under a `pcall` (a thrown error → `MigrationFailed`), and every failure after locking the legacy record clears our lock once (fix round 2); the clear touches only a `_session` with our job ID, and if it fails the lock expires after `SessionLockSeconds`. Every step is idempotent, so a crash between steps is repaired by the next open. A brand-new player gets one starter save "Tree Lot 1".
- **Tombstones:** `PersistenceService:markDeleted` (one `UpdateAsync`) refuses a save locked by another unexpired server (`SaveInUse`) or by this server (`SaveActive`); otherwise it sets `_deletedAt` and keeps all data. `load` refuses `_deletedAt` (`SaveDeleted`) and `_migratedTo` (`SaveMigrated`) without writing. Deleting needs the typed save name (case-insensitive, `SaveProfile.confirmMatches`).
- **Play and switch:** a save claims a plot keyed by its company ID, preferring the plot of the save it replaces; a switch saves and unloads the old save first. Without a free plot the player is teleported to another server of the place (`TeleportData.cm2NoFreePlot = {saveId, attempt}`, at most `MaxPlotTeleports` = 3 attempts); nothing is loaded in that case. `PlayerRemoving` and `BindToClose` call `leave(userId, true)` for every active save (the shadow included), which waits for an in-flight save action.
- **Shutdown:** `beginShutdown` refuses new save work; BindToClose waits for `pendingCount()` (final leaves plus busy actions and retrying final saves (`unloadingCount`)) up to 25 s.
- **Invite map (CM2-S2):** `InviteCodeService` does all I/O as `UpdateAsync` (reads return nil from the transform, so they write nothing; 3 attempts, 1 s and 2 s apart). `claim(saveId, exclude?)` draws up to `InviteClaimAttempts` (8) codes: a free key or a tombstone is written, the same save is success without a write, another save or the `exclude` code (no store call) counts as taken; else `InviteCodeUnavailable`. `release(code, saveId)` tombstones only its own code; `lookup(code)` returns the holding save, else `InviteCodeInvalid` (store error `LoadFailed`). The map is only an index: the record's `inviteCode` is the authority, so a stale map entry is harmless. A code is released only when the live record no longer uses it (after a saved change); without a healthy live record nothing is released.
- **Unlocked record changes (CM2-S2):** `PersistenceService:updateUnlocked(companyId, ownerUserId, mutate)` changes a record that no server holds, in one `UpdateAsync` without taking its lock: nil → `SaveNotFound`, `_deletedAt` → `SaveDeleted`, `_migratedTo` → `SaveNotFound`, any unexpired `_session` (this job included) → `SaveInUse`; otherwise it migrates a deep copy, drops an expired lock (a stalled holder then fails closed on its next save), applies `mutate` (a refusal writes nothing) and writes only a valid record. `SaveSlotService:_changeRecord` routes a team change through the live session when this server plays the save (`CompanyStateService:changeTeam(..., true)`, which saves at once), refuses with `SaveInUse` while a session here loads or unloads, and uses `updateUnlocked` otherwise. Joins while another server plays the save therefore return `SaveInUse`. `markDeleted` also returns `{memberUserIds, inviteCode}`, so a delete releases the code and drops the members' profile entries (best effort).
- **Shared sessions (CM2-S2):** several players on one server play one live session. Play attaches to a healthy session that another player here plays and that is not unloading (no load; the activation gets no state). A failed shared session is evicted (every player leaves it, it unloads once) before a member plays it again. Only the last leaver unloads the save; the plot is released only when nobody plays it here and no load of it waits (`_pendingLoads`). While the last leaver's unload is in flight (`_unloading`), a waiting load counts as `SessionBusy` and never loads, because the old session's lock release would clear the new session's same-job lock. Members load a save with `requireExisting` (a missing record is `SaveNotFound`, nothing is created) and without a name (the stored name is kept). A loaded or attached save that no longer lists the player returns `NotAMember` and drops the stale entry.
- **Save-to-server map (CM2-S3):** `SaveLocatorService` keeps one MemoryStore HashMap entry per played save (`CM2_SaveServers_v1`; Studio `CM2_SaveServers_v1_Studio`): held `{jobId, placeId, hostUserId, renewedAt}` with TTL `LocatorTtlSeconds` (90 s), released tombstone `{jobId, placeId, releasedAt}` with TTL 30 s, which counts as free. Authority: the DataStore session lock stays the only authority for writing a save; the map is a locator and a pre-check, so a wrong or missing entry can only send a player to the wrong server or show a stale row. Its atomic `UpdateAsync` lets at most one live server hold an entry, so two servers never both start loading one save. It fails open: on a store error (2 attempts, 1 s apart) Play loads as before and the lock decides. Play claims the entry before a load (another server's held entry → `SaveInUseElsewhere`, or `SaveInUse` for a Solo save, whose other session is stale); a renewal every `LocatorRenewSeconds` (30 s) re-claims every save played here, so two missed renewals are tolerated, and the TTL stays below `SessionLockSeconds` (120 s), so after a crash the entry is gone before the lock frees and Play shows `SessionLocked` meanwhile. The last successful unload, a failed load and the no-free-plot hand-off release the entry; a failed final save keeps it until it expires, like the lock. Host "X" is the owner when they play the save on that server, else its longest-playing member there. `Save.Teleport` and code joins of a save held elsewhere teleport into that public server (`TeleportOptions.ServerInstanceId = jobId`, `TeleportData.cm2Join = {saveId, code?}`); reserved servers are not used. The arrival data is untrusted: main shape-checks it and `arrive` needs the profile entry or the full `Save.Join` path with its lockout.
- **Purchase ledger (CM2-46a):** one record per player, `{ledgerVersion = 1, userId, robuxSpent = 0, pending = {[purchaseId] = {productKey, saveId, robux, at}}, done = {{purchaseId, productKey, saveId, robux, at}}, passesCounted = {[passKey] = true}, unlocks = {[productKey] = true}}`. Valid: integers ≥ 0 for `robuxSpent`, `robux`, `at`; `saveId` passes `SaveProfile.isSaveId`; product keys pass `ShopConfig.isKey`; `pending` at most `LedgerPendingCap` (20) entries; `done` a proper array of at most `LedgerDoneCap` (200), oldest first; the flag maps hold only `true`. Every call is one `UpdateAsync` (3 attempts, 1 s and 2 s apart) whose transform resets its results first, starts from a new record when none exists and writes nothing when nothing changes; an invalid record is `LedgerCorrupt` and never overwritten; a store error is `LoadFailed`. `bind` (before the grant) returns `Done`, `Bound`, `Other <saveId>` or `Full`; `finish` moves the purchase from `pending` to `done` once, adds its Robux and, for a per-player product, its unlock; `countPasses` adds each pass's price once. Co-op: a member's cash pack goes into the shared save; Robux spent and unlocks belong to the buyer. The profile is not changed.
- **Fail-closed surfacing (CM2-R3):** `CompanyStateService:setSessionFailedHandler` is called once per session, never while unloading, with `SessionLocked` (lock lost), `SaveFailed` (`NotLoaded` or `SaveFailClosedSeconds` without a save) or `InternalError`. `main.server.lua` sets `CompanyReady = false` and `CompanyError = <code>` for every player on that save; the HUD and the save picker show `Localization.saveErrorKey(code)`. Playing the save again reloads it once the lock is back.
- **Day cycle (CM2-G12a):** schema 20 adds `dayCycle = {day, elapsed}` to the company record (`src/shared/DayCycle.lua`; day ≥ 1, 0 ≤ elapsed < 1080 = 720 s day + 360 s night). `CompanyStateService:tickDayAll` (mixin `CompanyDayCycle`) advances it once per second only in healthy, loaded sessions that are not unloading, so there is no offline progress; a day rollover marks the session dirty without a revision bump. `main.server.lua` mirrors the clock into the player attributes `DayNumber`, `DayElapsed` and `DaySyncAt` (on activation, on rollover and every `SyncSeconds` 30 s; nil without an active save). Only the client writes `Lighting` (`ClockTime`, `OutdoorAmbient`, `src/client/DayNight.client.lua`); the server never does.

Persist financial request IDs/reward claims enough to prevent replay after reconnect; ledger should be append-bounded with aggregate counters. Avoid DataStore budget exhaustion by batching updates.

## 6. Deterministic game state
Every state mutation runs through an authoritative company command queue or equivalent serialization boundary. A command verifies revision, role, prerequisites, capacity, cash and idempotency, then applies all state changes together and emits one revision. Orders, unloads, reservations and sales must not be split across independently saved balances and inventory. Time-driven transitions use `os.time()` server timestamps. On load, reconcile due deliveries without passive income.

## 7. Collaboration permissions
Rewritten for CM2-S2 (PRODUCT_SPEC 2026-11-21 "Saves and multiplayer", OWNER DECIDED). A save has two roles, stored in the record's `members` map:
- **Owner** (the creator): every gameplay action and query, plus the owner-only save management.
- **Member** (joined by invite code): every gameplay action and query of the owner, on the same plot and the same cash balance. Members play while the owner is offline. `CompanyStateService` allows both roles every action of `MEMBER_ACTIONS`; anyone else gets `Forbidden`. A removed member is refused at once, because the live member map changed.
- **Owner-only** (`OwnerOnly` for members): Rename, Delete, RemoveMember, RegenerateCode, SetSize. Team, RemoveMember, RegenerateCode and SetSize act only on the requester's active save (`SaveNotActive`), and only on a healthy session (`CompanyUnavailable`). The owner cannot leave (`OwnerCannotLeave`) or be removed (`CannotRemoveOwner`); a member can leave (`Save.LeaveTeam`). Ownership transfer is deferred.
- **Joining:** `Save.Join {code}` adds a member only when the record's code equals the typed code and a seat is free. Wrong codes are locked out per player (10 per hour) and per server (60 per minute) before any store call.
- **Filter rule:** the save name was filtered for broadcast when the owner submitted it; stored text shown to other players needs filtering at retrieval, which needs the author online. So a member never receives the save name: the picker row and the HUD show "Shared lot from <owner username>" (Roblox usernames need no text filter). Display-time filtering is deferred to CM2-G15.
- Every membership change is checked against the authoritative record; personal saves never implicitly share funds.
