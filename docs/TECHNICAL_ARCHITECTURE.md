## 2. Authority and service boundaries
- SessionService: player/company join, ownership, lifecycle and cleanup (implemented as `SaveSlotService`; its save-to-server map is `SaveLocatorService`, CM2-S3).
- CompanyService: save ownership and membership (Solo/Duo/Trio/Quad, owner + members, 5-digit invite code, one server per save; PRODUCT_SPEC.md, owner decisions 2026-11-21).
- PlotService: plot allocation, boundaries, plot ownership and access.
- EconomyService: all money movement and immutable transaction IDs.
- SupplierService: catalog, unlocks, order validation and quote creation.
- DeliveryService: order state machine, ETA, arrival and unloading.
- InventoryService: unique stock item IDs, capacity and atomic lifecycle.
- PlacementService: bounded transforms, collision checks, plot persistence.
- PricingService: manual/auto prices and effective price at reservation time.
- CustomerService: NPC spawning, preferences, FSM and pathfinding budgets. CM2-N1: the walking customers' director is `CustomerNpcService` (FSM, queue, budget 4 per plot and 24 per server; headless-safe, world adapter injected); routes come from `NpcPath` (pure lot-frame router, no PathfindingService); the Roblox side is `CustomerNpcWorld` and `NpcAvatar`. Money and stock change only in `CompanyStateService`'s server-trusted `npc*` methods inside the company's critical section; no remote reaches them. Parking claims and session tokens are runtime only. CM2-N2: `checkout(companyId, plotId)`, prompt validated in `main.server` (`checkoutAt`). (Archive "Section 2, CustomerService (CM2-N1)".)
- CheckoutService: reserve, queue, finalize sale, rollback/cancel.
- EmployeeService: hire once, task assignment, job lease and completion.
- Staff (CM2-25/26): the director is `StaffNpcService` (headless like `CustomerNpcService`; injected `companies`, `plotOf`, `world`, `now`); staff ID `<companyId>|<role>`, budget 3 per plot and 18 per server (`GameConfig.Staff`), tick 0.25 s, FSM `StaffNpcService.Fsm`. Orders and stock change only in `CompanyStaff` (a mixin of `CompanyStateService`) inside the company's critical section; the Lot Worker carries orders as `Staff.CarrierUserId` 0 and restocks the runtime list `session.vacatedSpots` (not saved) through `PlacementService.stockFromBay`. `CustomerNpcService` serves the counter only while `staff:cashierReady(companyId)`. No wages: no staff code path debits cash. (Archive "Section 2, Staff (CM2-25/26)".)
- ProgressionService: prerequisites, HQ/parking/land unlocks.
- QuestService: event counters, rewards and idempotent claims.
- AnalyticsService: aggregate counters and bounded history.
- MonetizationService (CM2-46a, as built): headless with injected deps (`main.server.lua` wires `MarketplaceService` and `Players`). All 27 reference products live in `src/shared/ShopConfig.lua`; the owner creates the passes and products and enters their IDs (engineering creates and publishes nothing). `ProcessReceipt` grants a developer product only into the buyer's active, available save: bind the purchase to that save in the player ledger (`PurchaseLedgerService`), grant and save the company record with the receipt ID in it (`CompanyPurchases.grantPurchase`), record it done in the ledger, and only then return `PurchaseGranted`; any failure, unknown product ID or second call in flight returns `NotProcessedYet`; the purchase effect runs once per grant. Game passes are checked on join and after purchase; a pass perk applies while at least one of the save's players on this server owns it (runtime `setPerks`, never saved). Only the server prompts, never for an ID of 0 or a product with `ready = false`. No product grants a random reward; paid random items only from version 2 with PolicyService checks (PRODUCT_SPEC.md). (Archive "Section 2, MonetizationService (CM2-46a)".)
- PersistenceService: schema migrations, lock acquisition, save/retry/release.
- Lot layout (CM2-LOTLAY, PROVISIONAL, all in the lot frame x, z toward the road): `Placement.CarPark` (spaces `X` -5, 5, -15, 15, `Depth` 40, pad 8 x 12, door depth 33, `Apron` x -28..20, depth 27..59; CM2-PARK and CM2-TRAFFIC read only this table) and `Placement.Gate` (centred, pivot (0, 28), posts at x ±8.9). KeepClear ids: Stand, Checkout (-18..-5.5, 13..25: counter, cashier, queue L), Gate (-5.5..5.5, 13..27: the entrance path), Pickup, Spawn, Bays, Sign; the old `Parking` box is gone (the new boxes lie inside it, so saved layouts stay legal, no schema change). The counter stands at (-14, 16.5); `Npc.Path` holds `QueueSlots` (an L toward the gate), `StaffDepth` 14 and per space `EntryX` and `EntryDepth` 20 (the entry point inside the gate). `NpcPath` adds the raw front-fence boxes beside the gate (`gateFences`, inflated by `Clearance` as router obstacles after Bays) and the walk area (`inWalkArea`: the lot plus `FrontApronDepth` 8, z up to 35) that the router uses for its corner nodes; `NpcPath.parkingSpot` / `parkingPad` give the car pose and pad, `WorldService` reads them. Fence boxes: `Progression.fenceBoxes` returns Back, Left (full depth), FrontLeft, FrontRight and, from level 1, Right.

Use dependency injection or explicit initialization ordering; avoid circular requires. Shared modules are data and pure logic only, never grant currency.

All client-to-server calls are untrusted. Use a small versioned action protocol, not arbitrary client-defined price/cash/item payloads. Example action names:
Example action names (payloads, check order and error codes: `src/shared/Protocol.lua`, the code and each task's plan): `Supplier.RequestQuote`, `Supplier.PlaceOrder` (CM2-SUP: legacy payload or exactly `{lines}`, 1–12 lines; `UnexpectedField`, `InvalidLevel`/`InvalidTier`/`InvalidHQ`; `Progression.check` order `InvalidLevel`, `AlreadyOwned`, `NotNextLevel`, then `PrerequisitesNotMet`, `InsufficientReputation`, `InsufficientFunds`; debits once), `Company.Invite`, `Company.SetRole`, `Quest.Claim` (CM2-G11: `{slot, period}`; `InvalidQuest`, `QuestsRotated`, `AlreadyClaimed`, `BonusLocked`, `Incomplete`; reward added once as `QuestReward`; `Company.GetSummary.quests`), `Daily.Claim` (CM2-G11: `{}`; handled in `main.server.lua` by `DailyRewardService`, `companies:handle` answers `Forbidden`; rate limit 5 per 60 s, `ClaimBusy`, `AlreadyClaimed`, grant via `CompanyStateService:grantReward` kind `DailyReward`, a refused grant reverts the profile write), `Advent.Open` (CM2-A1: `{door}`; (Archive "Section 3, action catalogue".)
Shop actions (CM2-46a) travel through their own RemoteFunction `Remotes.ShopAction` and `MonetizationService:handle`, with the same envelope (`Protocol.validateShopRequest`): `Shop.Catalog` (`{}`) returns the products in config order with state `ComingSoon`, `Owned` or `Buy`, and `robuxSpent`; `Shop.Prompt` (`{productKey}`; `InvalidProduct`) checks `UnknownProduct`, `ComingSoon`, `AlreadyOwned`, `ShopUnavailable`, `NoActiveSave`, `BoostFull`, `PromptFailed`, rate limit 10 per 10 s (`RateLimited`). A successful prompt grants nothing: only the receipt does. (Archive "Section 3, shop actions".)

Request: `{version=1, requestId=<UUID>, action=<enum>, payload=<validated fields>}`. Response: `{ok, errorCode?, revision?, data?}`. Request IDs deduplicate financial actions within a session and persisted recent IDs where needed. Validate types, lengths, ranges, enum values, plot ownership, proximity where applicable, server-derived prices and role permissions. Per-action rate limits; never trust a client-supplied purchase cost, sale result, or inventory quantity.

Server->client: a one-way `Notify` RemoteEvent carries localized notice keys (customer reviews, wrong car, out of reach). Filtered state snapshots on join and revisioned deltas after mutations. Client can optimistically animate UI but server state wins. Avoid broadcasting private company details to other plots.

Schema is a proposal; existing `BusinessState.lua` currently uses a simpler v1 shape and must be migrated carefully before production. Keep all persisted numeric values finite, capped and serializable. Store transforms as numeric arrays, not Instances/CFrames.

**Schema history (CM2-S1 to CM2-45; every field rule and migration: the archive; `BusinessState.lua` is the authority, `SCHEMA_VERSION = 23`).** Each bump fails closed on older servers (shut them down when it ships), keeps persisted numbers finite and capped, migrates by a pure function in `BusinessState` and never overwrites a record that fails `validate`.
- **Save slots (CM2-S1):** each player owns a profile (`SaveProfile.VERSION = 1`: `saves` with `saveId`, `name`, `role`, `size`, `createdAt`, `lastPlayedAt`; `nextSaveNumber`, `lastSaveId`, `legacyState`, `legacySaveId`, `recentCreates`), at most 50 entries (`GameConfig.Saves.MaxSavesPerPlayer`); names trimmed, 1–24 code points, no control characters or `#`, filtered with `TextService`. Company ID `save:<saveId>`; save ID `<ownerUserId>_<16 lowercase hex>`, at most 36 chars, never reused, deleted saves keep a tombstone. Schema 11 adds `saveName` and `saveSize`; `validate` ignores `_session`, `_deletedAt`, `_migratedTo`, `_migratedAt`, `_migratedFrom`.
- **Co-op (CM2-S2, schema 12):** `members` maps `userIdText` to `Owner` or `Member` (exactly one Owner; seats Solo 1, Duo 2, Trio 3, Quad 4); `inviteCode` nil or `^[1-9]%d%d%d%d$`, nil for Solo; pure helpers `addMember`, `removeMember`, `setInviteCode`, `setSaveSize`; a member's profile entry counts toward the 50-save cap.
- **Schemas 13 to 23:** 13 (CM2-G14) `bays` replace `stock` (4 bays, one order = one bay; `Receiving.lua`, `Stocking.lua`, `PlacementService.stockFromBay`/`storeBack`; placements in the lot frame); 14 (N2) `walkedOutCustomers`; 15 (G15) `reviews`, `likes`, `queueSeconds`; 16 (25/26) `staff`, `staffEnergy`, `breakArea`; 17 (46a) `purchases = {receipts, owned, boosts}`; 18 (49) `tutorial = {step, skipped}`; 19 (G9a) `progression = {lotExpansion, parkingTier, hqLevel}`; 20 (G12a) `dayCycle`; 21 (G11) `quests = {period, progress, claimed}`; 22 (A1) `decorInventory`; 23 (45) `eventPurchases`.

## 5. Persistence and concurrency
DataStore keys scoped by company ID; use UpdateAsync-based session lock with job ID and expiry/heartbeat, not a naive GetAsync/SetAsync last-write-wins. Acquire lock before enabling writes; renew while active; release at leave/shutdown; recover expired locks with a safety margin. Save after significant actions (debounced) plus periodic autosave and BindToClose; retries with exponential backoff and budget awareness. If load fails, block financial actions instead of creating a fresh default and overwriting existing progress. Use versioned migration functions and backup/rollback strategy. Shared-company single-writer policy; conflicts must not fork balances.

**Implemented policy (2026-11-21):** a company record is one DataStore key; mutations run inside the company critical section without yielding and only mark the session dirty. `flushDirty()` writes dirty sessions every `SaveFlushSeconds` (15 s) and re-saves every session at least every `AutosaveSeconds` (60 s) to renew the `SessionLockSeconds` (120 s) lock. Leave, switch and shutdown save finally (CM2-R5); a failed final save is retried (`GameConfig.UnloadRetry`, at most 18 s after shutdown begins); lock and map entry are released only after a successful save; a switch away from an unsavable save keeps the player on it (`SwitchSaveFailed`); Play during the retry gets `SessionBusy`. A crash loses at most one flush interval, never a debit without its effect. Lock loss, an invalid record or `SaveFailClosedSeconds` (90 s) without a save stops mutations; a runtime error in a critical section fails that session closed. Robux receipts save the record right after the grant and return `PurchaseGranted` only after that save and the ledger succeed (section 2). (Archive "Section 5, implemented policy".)

**Save slots (CM2-S1, implemented 2026-11-22).** `SaveSlotService` fills the SessionService role of section 2: profile I/O, the legacy migration call, the `Save.*` actions (`Remotes.SaveAction`), play, switch, leave, the teleport seam and the active-save registry. Since CM2-RF the code is split into `SaveSlotService` (core) and the parts `SaveSlotPicker`, `SaveSlotTeam`, `SaveSlotCrossServer` and `SaveSlotShared`; the parts add methods to the one class.

| Store | Key | Holds |
|---|---|---|

| same store | `company:save:<saveId>` | One company record per save, with its own session lock |

Every key contains the user ID as a fixed substring, so RTBF erasure templates can match it. Store names are not scoped by environment (out of scope). `Profiles_v1` held only Studio test profiles with old 32-hex save IDs that the current `isSaveId` rejects; it is abandoned and never read.

**Key budget.** Roblox DataStore keys are limited to 50 characters (`KeyNameLimit`, `SaveProfile.KEY_MAX_LENGTH`). The worst case is a 19-digit user ID:

| Family | Format | Max chars |
|---|---|---|
| Company legacy | `company:personal:<userId>` | 36 |
| Company save | `company:save:<userId>_<16hex>` | 49 |
| Profile | `profile:<userId>` | 27 |
| S2 invite code (store `ChristmasMarket2_Invites_v1`) | `invite:<code>` | 12 |
| Purchase ledger (store `ChristmasMarket2_Purchases_v1`, CM2-46a) | `purchases:<userId>` | 29 |
| S3 save-to-server map (MemoryStore HashMap `CM2_SaveServers_v1`, limit 128; `SaveLocatorService.keyFor`) | `save:<saveId>` | 41 |
| Leaderboard player (stores `ChristmasMarket2_LB_<Key>_v1`, CM2-G12b) | `player_<userId>` | 26 |
| Leaderboard save (stores `ChristmasMarket2_LB_<Key>_v1`, CM2-G12b) | `save_<saveId>` | 41 |

Rule for S2 and S3: a key holding a save ID gets a prefix of at most 14 chars; a key holding a user ID, at most 31. Every new key family adds a row here and a case to the key-length test (SaveSlotService_Test "keeps every key within 50 characters for a 19-digit user ID"). S2 member lists stay inside the company record (no new key). Every fake DataStore in the tests enforces the 50-character limit.
- **Lock-free profile:** every profile change is one `UpdateAsync` transform applied to the stored value (3 attempts, 1 s and 2 s apart), so a second server can never lose an update and S2 can write to another player's profile. Transforms reset their results at the start (they can run more than once). An unreadable profile fails with `ProfileUnavailable`, an invalid one with `ProfileCorrupt`; neither is ever overwritten with a fresh default.
- **Legacy migration** (`PersistenceService:migrateLegacy(userId, saveId, saveName)`, called on the first profile open while `legacyState = "Pending"`): four idempotent steps, each one `UpdateAsync`: take a copy of `company:personal:<userId>` without its lock, migrate it as `save:<saveId>` (`saveSize = "Solo"`, `_migratedFrom`), write it once, then mark the legacy record `_migratedTo` and clear our lock (its data stays). Codes `NoLegacy`, `SessionLocked`, `MigrationFailed`, `MigrationConflict`, `LoadFailed`; every failure after locking clears our lock once. A brand-new player gets one starter save "Tree Lot 1". (Archive "Section 5, legacy migration".)
- **Tombstones:** `PersistenceService:markDeleted` (one `UpdateAsync`) refuses a save locked by another unexpired server (`SaveInUse`) or by this server (`SaveActive`); otherwise it sets `_deletedAt` and keeps all data. `load` refuses `_deletedAt` (`SaveDeleted`) and `_migratedTo` (`SaveMigrated`) without writing. Deleting needs the typed save name (case-insensitive, `SaveProfile.confirmMatches`).
- **Play and switch:** a save claims a plot keyed by its company ID, preferring the plot of the save it replaces; a switch saves and unloads the old save first. Without a free plot the player is teleported to another server (`TeleportData.cm2NoFreePlot = {saveId, attempt}`, at most `MaxPlotTeleports` = 3). `PlayerRemoving` and `BindToClose` call `leave(userId, true)` for every active save. **Plot picker (CM2-PP, `docs/archive/plans/CM2-PP.md`):** `Save.Plots {saveId}` (20 per 10 s) lists the plots (`name` is the lot sign's public text); `Save.Play {saveId, plotId?}` claims exactly the chosen plot while it is free (`PlotTaken` when taken while another is free); attach paths, `Save.FinderStart`, `Save.Teleport` arrivals, Studio hooks and `runPlaytest` keep the automatic claim; a `cm2NoFreePlot` arrival sets the attribute `PlotPickSaveId` and the client opens the picker. The profile entry gains `lastPlotId`. (Archive "Section 5, play and switch and plot picker".)
- **Shutdown:** `beginShutdown` refuses new save work; BindToClose waits for `pendingCount()` (final leaves plus busy actions and retrying final saves (`unloadingCount`)) up to 25 s.
- **Invite map (CM2-S2):** `InviteCodeService` does all I/O as `UpdateAsync` (3 attempts); `claim(saveId, exclude?)` draws up to 8 codes (a free key or tombstone is written, else `InviteCodeUnavailable`), `release(code, saveId)` tombstones only its own code, `lookup(code)` returns the holding save, else `InviteCodeInvalid`. The map is only an index: the record's `inviteCode` is the authority; a code is released only when the live record no longer uses it. (Archive "Section 5, invite map".)
- **Unlocked record changes (CM2-S2):** `PersistenceService:updateUnlocked(companyId, ownerUserId, mutate)` changes a record no server holds in one `UpdateAsync` without its lock (`SaveNotFound`, `SaveDeleted`, any unexpired `_session` is `SaveInUse`; writes only a valid record). `SaveSlotService:_changeRecord` routes a team change through the live session when this server plays the save (`changeTeam`, saves at once), refuses with `SaveInUse` while a session here loads or unloads, else uses `updateUnlocked`. `markDeleted` also returns `{memberUserIds, inviteCode}`. (Archive "Section 5, unlocked record changes".)
- **Shared sessions (CM2-S2):** several players on one server play one live session; Play attaches to a healthy session another player here plays. A failed shared session is evicted before a member plays it again; only the last leaver unloads, and the plot is released only when nobody plays it here and no load waits (`_pendingLoads`). While an unload is in flight (`_unloading`) a waiting load is `SessionBusy`. Members load with `requireExisting` and without a name; a save that no longer lists the player returns `NotAMember`. (Archive "Section 5, shared sessions".)
- **Save-to-server map (CM2-S3):** `SaveLocatorService` keeps one MemoryStore HashMap entry per played save (`CM2_SaveServers_v1`; Studio `_Studio`): held `{jobId, placeId, hostUserId, renewedAt}` with TTL `LocatorTtlSeconds` (90 s), released tombstone with TTL 30 s. The DataStore session lock stays the only write authority; the map is a locator and pre-check and fails open on a store error. Play claims the entry before a load (`SaveInUseElsewhere`, or `SaveInUse` for Solo); a renewal every `LocatorRenewSeconds` (30 s); the TTL stays below `SessionLockSeconds` (120 s). `Save.Teleport` and code joins of a save held elsewhere teleport into that public server (`ServerInstanceId = jobId`, `TeleportData.cm2Join`); the arrival data is untrusted and shape-checked. (Archive "Section 5, save-to-server map".)
- **Purchase ledger (CM2-46a):** one record per player, `{ledgerVersion = 1, userId, robuxSpent, pending, done, passesCounted, unlocks}` (`pending` at most `LedgerPendingCap` 20, `done` at most `LedgerDoneCap` 200). Every call is one `UpdateAsync` (3 attempts) that writes nothing when nothing changes; an invalid record is `LedgerCorrupt` and never overwritten, a store error `LoadFailed`. `bind` (before the grant) returns `Done`, `Bound`, `Other <saveId>` or `Full`; `finish` moves the purchase to `done` once and adds its Robux and any per-player unlock; `countPasses` adds each pass's price once. A member's cash pack goes into the shared save; Robux spent and unlocks belong to the buyer. (Archive "Section 5, purchase ledger".)
- **Fail-closed surfacing (CM2-R3):** `CompanyStateService:setSessionFailedHandler` is called once per session, never while unloading, with `SessionLocked` (lock lost), `SaveFailed` (`NotLoaded` or `SaveFailClosedSeconds` without a save) or `InternalError`. `main.server.lua` sets `CompanyReady = false` and `CompanyError = <code>` for every player on that save; the HUD and the save picker show `Localization.saveErrorKey(code)`. Playing the save again reloads it once the lock is back.
- **Leaderboards (CM2-G12b):** `LeaderboardService` caches board values on the server (Cash earned and Reputation per save, Robux spent and Hours played per player). A flush every `WriteIntervalSeconds` (120 s) writes only changed entries (at most `MaxWritesPerFlush` 24, only while the `OrderedWrite` budget is at least `MinWriteBudget` 10; playtime as `IncrementAsync` deltas); every `ReadIntervalSeconds` (180 s) each board reads its top `RankDepth` (100) and publishes the top 10 as JSON in an attribute of `ReplicatedStorage.Leaderboards` plus each player's `Lb<Key>Value` / `Lb<Key>Rank`; a failed read keeps the old ranks. `PlayerRemoving` and BindToClose flush best effort. (Archive "Section 5, leaderboards".)
- **Day cycle (CM2-G12a):** schema 20 `dayCycle = {day, elapsed}` (`src/shared/DayCycle.lua`; 720 s day + 360 s night). `CompanyStateService:tickDayAll` (mixin `CompanyDayCycle`) advances it once per second only in healthy, loaded sessions, so there is no offline progress. `main.server.lua` mirrors it into the player attributes `DayNumber`, `DayElapsed`, `DaySyncAt` (every 30 s and on rollover); only the client writes `Lighting` (`src/client/DayNight.client.lua`). (Archive "Section 5, day cycle".)
- **Quest board and daily streak (CM2-G11, `docs/archive/plans/CM2-G11.md`):** schema 21 `quests = {period, progress, claimed}` (`period = floor(clock / GameConfig.Quests.RotationSeconds)`, 4 progress integers, 4 booleans; index 4 is the bonus; period 0 is stale and the first note, claim or test hook builds the board). The player profile gains `daily = {lastDay, streak}` (nil = never claimed): `SaveSlotService:claimDaily` writes it in one `UpdateAsync` as the once-per-day guard, `revertDaily` restores the previous value only while the stored field is still this claim. ## 6. Deterministic game state
Every state mutation runs through an authoritative company command queue or equivalent serialization boundary. A command verifies revision, role, prerequisites, capacity, cash and idempotency, then applies all state changes together and emits one revision. Orders, unloads, reservations and sales must not be split across independently saved balances and inventory. Time-driven transitions use `os.time()` server timestamps. ## 7. Collaboration permissions
Rewritten for CM2-S2 (PRODUCT_SPEC 2026-11-21 "Saves and multiplayer", OWNER DECIDED). A save has two roles, stored in the record's `members` map:
- **Owner** (the creator): every gameplay action and query, plus the owner-only save management.
- **Member** (joined by invite code): every gameplay action and query of the owner, on the same plot and the same cash balance. Members play while the owner is offline. `CompanyStateService` allows both roles every action of `MEMBER_ACTIONS`; anyone else gets `Forbidden`. A removed member is refused at once, because the live member map changed.
- **Owner-only** (`OwnerOnly` for members): Rename, Delete, RemoveMember, RegenerateCode, SetSize. Team, RemoveMember, RegenerateCode and SetSize act only on the requester's active save (`SaveNotActive`), and only on a healthy session (`CompanyUnavailable`). The owner cannot leave (`OwnerCannotLeave`) or be removed (`CannotRemoveOwner`); a member can leave (`Save.LeaveTeam`). Ownership transfer is deferred.
- **Joining:** `Save.Join {code}` adds a member only when the record's code equals the typed code and a seat is free. Wrong codes are locked out per player (10 per hour) and per server (60 per minute) before any store call.
- **Filter rule:** the save name was filtered for broadcast when the owner submitted it; stored text shown to other players needs filtering at retrieval, which needs the author online. So a member never receives the save name: the picker row and the HUD show "Shared lot from <owner username>" (Roblox usernames need no text filter). Display-time filtering is deferred to CM2-G15.
- Every membership change is checked against the authoritative record; personal saves never implicitly share funds.
